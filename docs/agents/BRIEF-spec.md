# Brief: the specification, version 2026-10-24

Read docs/agents/COMMON.md first.

## Goal

Write the OpenHAL specification as a dated, formal protocol specification in the voice of docs/DESIGN.md: formal, exact and short. It covers the device file format (today's spec/SPEC.md) and the hub protocol (docs/adr/0015-openhal-hub-protocol.md). It must read like a well-run open protocol specification. It is never called a standard, and it states it is not affiliated with Anthropic or MHS.

## Deliverables

1. **`spec/2026-10-24/`** with one Markdown file per section, in this order:
   - `index.md`. Introduction, status (draft), conformance keywords (MUST, SHOULD and MAY per RFC 2119 and RFC 8174, with the standard sentence), and terminology. Defined terms are capitalized and listed in a glossary: Hub, Client, Device, Device File, Driver, Safety Kernel, Grant, Principal, Conformance Level, Confirmation Request.
   - `architecture.md`. Roles and the one-hub model. A sequence diagram as a Mermaid block: Client to Hub to Safety Kernel to Driver to Device, for one blocked and one granted `hal/write`.
   - `basic/lifecycle.md`, `basic/transports.md` and `basic/messages.md`. Initialize and version negotiation, WebSocket and stdio, JSON-RPC rules, every method and notification with params and results, and an example exchange for each.
   - `device-files.md`. Move the normative content of spec/SPEC.md here, rewritten to use MUST, SHOULD and MAY where it states requirements. Keep every rule, so nothing normative may be lost.
   - `safety.md`. Requirements on a Safety Kernel. The check order, unknown values never pass, grants, stop and unlock, confirmations, and limits provenance. Then the full error code registry from the ADR as a table.
   - `drivers.md`. The driver interface (see docs/drivers/WRITING-A-DRIVER.md and openhal/drivers/base.py) and the three conformance levels with what the conformance suite tests for each.
   - `routines.md`. From docs/adr/0007 and openhal/routines.
   - `security.md`. From docs/THREAT_MODEL.md and docs/SAFETY.md. Local-only by default, tokens, prompt injection as data, and what is not guaranteed.
   - `changelog.md`. 2026-10-24, the first draft.
   - `schema.md` and `schema.json` are generated by the protocol workstream. Link to them but don't write them.
2. **`spec/versions.json`**: `{ "latest": "2026-10-24", "versions": [{ "version": "2026-10-24", "status": "draft" }] }`.
3. **`spec/SPEC.md`** becomes a short pointer to `spec/2026-10-24/device-files.md`, so old links keep working. `spec/CHANGELOG.md` points to the dated changelog. `spec/schema/device-file.schema.json` stays where it is.
4. **`tests/spec/test_spec_names.py`**
   - Every `hal/...` method or notification name and every UPPER_SNAKE error name in spec/2026-10-24/*.md must exist in the ADR 0015 tables, and every ADR name must appear in the spec.
   - Every numeric code shown next to a name must match.
   - Parse the ADR Markdown tables. Once openhal/protocol exists in main, the orchestrator will point the test at the registry.
5. **Example exchanges** use the exact ADR formats, including the LIMIT_EXCEEDED reason template.

## Style

- Short declarative sentences. Requirements as numbered lists where it helps.
- No marketing.
- Headings in sentence case.
- Tables for registries and parameters.

## Files you own

spec/ (except spec/2026-10-24/schema.json and schema.md, and spec/schema/), and tests/spec/test_spec_names.py.

## Not yours

Code, the website, README.md, docs/DESIGN.md and the ADR. If the ADR is wrong or incomplete, propose the fix in your report and don't change the ADR.
